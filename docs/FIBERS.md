# Ported code that can block

The readable port (`src/port/`) replaces the game's recompiled functions one at a time. Recompiled code can be interrupted anywhere by the EE scheduler: a thread switch unwinds every host frame (`EeDispatcherTransfer`) and the thread later re-enters mid-function through `switch (ctx->pc)`, because everything the code needs is in the R5900 context and the guest stack. A hand-written C++ function keeps locals in host frames, so a switch under it would lose the rest of the function. About 29% of the game's functions can reach a switch (a semaphore wait, a yield, a vsync or RPC wait, `SignalSema` readying a higher-priority thread, ...), often only through `malloc`, `free`, `new` or `delete`. This is how they are ported anyway.

## Mechanism (`patches/0137-ee-fibers.patch`)

* A function that can reach a switch (`mm::blocking::at<address>` in `src/port/game_functions.h`, generated by `tools/port_gen.py` from the `blocking` column of `config/port_status.csv` and from `config/blocking_extra.txt`) is entered through `Wrapper::entry` in `src/port/abi.h`. If the scheduler is running a guest thread, the body runs on a **fiber** (`GuestFiber`, a Windows fiber) belonging to the thread's execution slot (`EeScheduler::runOnFiber`).
* All guest code a ported function calls goes through `port::callGuest`, which enters it with `EeScheduler::callOnFiber`. If a switch unwinds that guest code, the exception stops there, **outside any catch block** (the host's exception state is per thread, not per fiber), and the fiber is **parked** with its C++ frames intact (`parkFiber`). The dispatcher goes on as it always does.
* When the thread is next chosen, `EeScheduler::run` resumes the parked fiber instead of entering `ctx->pc`. `callOnFiber` carries on driving the guest code from `ctx->pc` until it returns to the sentinel address, exactly as the dispatcher would have, and the ported function continues.
* A ported function on a fiber is **not** under the no-preempt rule: checkpoints fire in the guest code it calls, and `finishGuestCall` yields (`EeScheduler::yieldIfDue`) when the callee handed the call back with a checkpoint due. So a spin loop that waits for an interrupt or another thread works, and vsync and other interrupts are delivered while ported code runs. Ported code that is not on a fiber keeps the old rule (no checkpoints while it runs, a switch is the fatal error `reachedThreadSwitch`).
* Per-fiber state moves with the fiber: the scheduler's no-preempt depth, and the port layer's `g_call` (hooks `fiberEnter` and `fiberLeave`, `src/port/port.cpp`).
* A thread that exits or is terminated while its fiber is parked drops the fiber (frames are not unwound). A thread that exits from inside its own fiber abandons it. Invocations (interrupt handlers, RPC callbacks and the like) are a `std::deque` on the thread so a context keeps its address while a fiber points to it, and each invocation level can have its own fiber.
* `PS2X_FIBERS=0` turns it all off (a fiber function then runs directly and a switch under it is the fatal error). `PS2X_FIBER_STATS=1` prints, every 5 seconds, how many fibers started, parked, yielded at a checkpoint and resumed.

## Waiting loops that run natively

Recompiled code charges the scheduler 32 cycles at every loop's back branch (`eeCheckpointDue`), and the scheduler drives the timers, the interrupts and the IOP (a module starting, an RPC server registering) from the cycles it is charged. A ported function that waits in a native loop has to charge them too: `port::checkpoint()` once per turn of a loop that waits for time or for another thread (it charges 32 cycles and yields when a checkpoint is due, as a back branch does), `port::accountCycles(n)` for a pause of known length. A native loop that charges nothing starves what it waits for. The first run with every function ported stalled at boot for this reason: `Sound_Init` paused 10000 empty turns after each RPC bind, the pause charged nothing, and the sound server on the IOP never registered. The difftest cannot see it, since its replay never waits for the IOP; a visible run does. Loops that poll hardware registers the runtime answers from its own state (the IPU control register in the movie player) need nothing.

`MMPC_PORT_TRACE=<names|0xADDR|all>` prints a line when a ported function is entered and left, which shows where a stall stands (an "enter" with no "leave"). It sees only the calls that go through the function table (from recompiled code, a vtable slot, `port::callGuest`); a ported function calling another ported one is a direct C++ call and prints nothing. The same holds for the debug wrappers in `src/overrides/` (`MMPC_TRACE`, `MMPC_TRACE_CALLS`, the movie skip): they wrap what is registered at an address, so they miss direct calls. The movie skip therefore hooks the SDK's disc search (a `.PSS` path finds nothing) instead of the game's movie functions.

## Checking

The runtime has unit tests in `ps2xTest` (`ps2_runtime_kernel_tests.cpp`): a fiber function waits on a semaphore and carries on; waits twice; is terminated while parked; exits from inside its fiber; has an invocation run on its thread while parked. Functions that complete without switching are checked by the usual `pipeline.py capture` and `difftest`, which replay them directly (no fibers). The replay restores what the runtime keeps outside RDRAM before every run (the guest heap's bookkeeping and the file descriptor counter, `patches/0138`), so a function that allocates or opens a file gets the same block and descriptor in the original and in the port. A record whose call loops on a descriptor that only the live game had open (the game's own `while (sceRead() < 0)` retry) cannot finish in the headless replay, even in the original code; such records are set aside (`work/difftest_hung/`) and the function is checked by visible runs instead. Functions that always block (thread entries, the main loop) get no records; they stay `ported` in `docs/PORT_STATUS.md` until one exists and are checked by visible runs and by `MMPC_PORT_DISABLE=<address>` against the generated version.
