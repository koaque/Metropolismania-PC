# src/port: the readable port

Hand-written C++ versions of Metropolismania's own functions. Each one replaces the recompiled
(generated) function at the same address while the rest of the game keeps running as recompiled
code, so the game stays playable at every step. A ported function only counts as done once it
matches its original exactly on the differential tests.

## Files

| File | What it is |
|---|---|
| `guest.h` | Guest memory access (`port::host`, `port::load`, `port::store`), `mm::GuestPtr<T>` (a 32-bit game pointer) and `mm::ps2f` (a float with the PS2 FPU's arithmetic) |
| `abi.h` | `PORT_FN(Name)` and `port::callGuest`: the calling convention between ported and recompiled code; `port::GuestLocal<T>` for a local a guest function gets a pointer to |
| `vu0.h` | VU0 macro mode for ported code: the context's registers and the runtime's vector operations |
| `sdk.h` | Sony SDK routines game code calls (libc, libm, libvu0, the compiler's float conversion), reached through `port::callGuest` until plan step P7 ports them |
| `port.h`, `port.cpp` | The registry of ported functions and `port::install` (called by the override module) |
| `difftest.h`, `difftest.cpp` | Capture and replay of differential tests |
| `game_types.h` | Generated by `tools/port_gen.py` from `config/types/*.h`: the game's structs as overlays on guest memory |
| `game_functions.h` | Generated by `tools/port_gen.py` from `config/signatures.txt`: every game function's address and prototype |
| `game_globals.h` | Addresses of global data used by ported code |
| `<subsystem>.cpp` | Ported functions, one file per subsystem (as in `docs/map/`) |

Do not edit the two generated headers; `pipeline.py stage` rewrites them.

## Porting a function

1. Read its decompile (`work/decomp/<ADDR>.c`, after `pipeline.py map`) and its page in `docs/map/`.
   Fix the prototype in `config/signatures.txt` first if it is wrong.
2. Write it in `src/port/<subsystem>.cpp` inside `namespace mm`, named like the game function
   without `mm_` and with exactly the prototype from `game_functions.h`. Add `PORT_FN(Name);`.
3. Rules that keep it exact:
   - Floats are `ps2f`. Never do arithmetic on plain `float`.
   - Integer division by a value that comes from data uses `divide` and `remainder` (`guest.h`):
     the R5900 gives a defined result for a zero divisor, where C++ would trap.
   - Pointers are `GuestPtr<T>`, in prototypes and struct fields alike. Index them and add to them
     as guest pointers (`map->objects + i`, `map->tiles[t]`): the arithmetic happens on the 32-bit
     guest address and every access is masked into RDRAM, as in the recompiled code, so a wild
     index wraps instead of crashing. Address 0 is plain memory; test for null with `if (p)`.
   - Game data stays in guest memory: use the structs from `game_types.h`, `port::load`/`store`
     and the addresses in `game_globals.h`, not host copies that outlive the call.
   - Call other game functions by name (`Family_InCity(f)`). Unported ones go through the
     function table to the recompiled code; ported ones are plain C++ calls.
   - Some functions leave the result register as they find it (a call that ends in a callee's
     work, a helper that returns nothing). Their port returns `port::guestV0()`. A caller that gets
     its own result from such a call has to put it there first with `port::setGuestV0(...)`:
     the recompiled caller had the callee's value in v0, a ported caller calling a ported callee
     does not (`mm_MemberStatus_OnLevel12` returns the status address through
     `mm_Family_AddFriendship`).
   - Nothing that can block or switch threads (the `Blocks` column in `docs/map/`): those
     functions wait for plan step P6.
   - VU0 registers are shared state. Some game code reads lanes it never wrote: the w of vf6 in
     `mm_Math_TriangleNormal` (it ends up in the result's w), vf3.w in `mm_BldgWasteland_Tick` and
     `mm_Collide_PointInTriangle`, and all of vf12 in `mm_BldgField_Draw` (its matrix product stores
     a fourth row it never computed). A ported function that uses VU0 must leave vf1-vf31, ACC and Q
     exactly as the original does: write it with `vu0.h`, which works on the context's registers
     with the runtime's own operations, one helper per instruction form. A static scan of the 87
     functions that use VU0 found no reads of the MAC, status or clipping flags across functions,
     so those need not match.
   - A local whose address the original passes to another function (it lived in the original's
     stack frame) goes in a `port::GuestLocal<T>`: guest memory below the guest stack pointer,
     which moves down for the scope so callees stack below it.
   - When the original only partly fills such a local and VU0 then loads all of it (the lanes it
     never wrote are whatever the stack held), declare the locals so they take the original's
     slots: the first `GuestLocal` lands at entry sp - 16, each next one 16 bytes (or its size)
     below. `mm_Map_SampleHeight` and `mm_Person_ProbeTile` do this. Declare them before the
     first guest call, so that the callee's frame stays below them as it did in the original.
   - A function that calls such a function (directly, or through `callGuest`) reserves its own
     original frame first with `port::GuestFrame<Size>` (the size from its `addiu $sp, $sp, -Size`),
     so the callee's slots land over the same leftover stack data (`mm_Char2_Draw`).
   - The address of such a frame can reach hardware state: `mm_Sky_Load` builds its DMA packet on
     the stack and `mm_Dma_KickVif1Now` writes the packet's address into the chain buffer that the
     difftest compares, so `mm_CityCamera_BaseCtor` and `mm_CityCamera_ctor` declare their own
     (otherwise empty) 0x20-byte frames.
4. `pipeline.py stage`, `build`, then `pipeline.py capture --functions <Name>` (a visible run that
   records calls of the original) and `pipeline.py difftest`. Every record must be exact. For a
   function that runs every frame, add `--every N` so the records spread over boot, title and city
   instead of all coming from the first frames. Most of the game only runs in a developed city: copy your own
   saves into the runner with `python tools/mc_extract.py <card.ps2>` (a PCSX2 memory card image)
   and capture with `--autoplay load`, which loads the newest one, or `--autoplay explore`, which
   then plays the city at random (talks, menus, building) so far more functions get called.
   `MMPC_CALL_COUNTS=<file>` on any run writes how often each game function was called.
   For a function with branches on its float or integer arguments, also run `pipeline.py difftest
   --fuzz 30 --fuzz-functions <Name>`: every record is replayed 30 more times with mutated arguments
   (pointers unchanged), which reaches cases the recorded calls never take. Leave out functions whose
   integer arguments are loop bounds, sizes or table indexes (the building draws' layer index sends
   writes into hardware space, which the port refuses).
5. Mark it in `config/port_status.csv` (`ported`, then `verified` once difftested).

`MMPC_PORT_DISABLE=0xADDR,...` (or `all`) runs the generated code again for chosen functions, to
bisect a problem.

## What the difftest compares

Each record holds the CPU state at a call and all of RDRAM and the scratchpad. The replay runs the
original and the ported function from that same state and compares guest memory (except the free
stack below the entry stack pointer), the result register, the stack pointer, the return address,
the callee-saved registers and the VU0 registers (vf1-vf31, ACC, Q). Effects outside guest memory
(GS, sound, files) are not compared yet. Records are game-derived data and stay in `work/difftest/`.

Paths the explore runs never reach get records made from captured ones with `tools/record_patch.py`:
the same state with an argument register or a few RDRAM words changed (a building with workers to
demolish, a counter about to run out, a listener moved next to the vehicles), or a captured record
copied under another function's name with that function's arguments (a callee the capture only
reached through its caller). Such records are named `sNN.mmdt`. `pipeline.py difftest --changes
<Names>` lists the RDRAM each record's original run changed, and its v0 for a function with an
integer result, which shows whether a made record reaches the path it was made for: a record that
passes but changes nothing (and returns nothing compared) proves nothing, and records that all
return the same value may all take the same path. `--only <Names>` replays just those functions (results.json is then left
alone), and a replay that does not return within 60 s (`MMPC_DIFFTEST_HANG_SECONDS`) is reported as
HANG and ends the run: a made state can send the original into a wait that never ends, for instance
when it reaches blocking code. To find why a record fails: `MMPC_DIFFTEST_RANGES=<n>` lists more of the differing
RDRAM ranges, `MMPC_DIFFTEST_DUMP=<hex address>:<words>` prints those words of both runs, and
`MMPC_DIFFTEST_TRACE=<function names>` prints the argument registers of every call to those functions in the original run
and in the ported one, which shows what the two hand a callee.
`MMPC_DIFFTEST_WATCH=<hex address>` adds the word there after every traced call (the first call after which the two runs differ
points at the writer), and `MMPC_PORT_DISABLE=0xADDR,...` keeps those functions generated in the port run too.
Warm records: a record named `warm<N>_...mmdt` is first advanced by N calls of the original (same arguments, memory and heap
bookkeeping carried over) and the replay compares the call after that; it reaches the later steps of a function that works
in steps over many frames, which a capture of the first frames cannot.

Some state lives in the runtime, outside RDRAM, and the replay does not reset it between the original's run
and the ported one's: the guest heap and the file descriptors are saved and restored (patch 0138), but the
RPC bind counter and server descriptors of the sound driver, the memory card's file numbers and the family
record cache are not. Records that depend on them differ in a few bytes the game only keeps (`Sound_Init`,
`McSave_WriteIconSys`, `PauseMenu_StateSave`: ignore rules in `difftest.cpp`) or hang in the original too
(a family not in the cache is read from the disc, which the replay never finishes: `Words_LoadForFamily`).
The VU0 registers are not compared for functions that call a ported callee where the generated one left
scratch values (`Person_ChooseDestination`, `CityCursor_Update`, the two talk person constructors).
A new save's name carries the console clock in seconds, which ticks between the two runs: the last digits of the sixteen
name slots are not compared for `McManager_NewSaveName`, `McManager_PrepareNewSlot` and the pause menu's slot list.

Functions with no record the replay can finish stay at "ported" in `docs/PORT_STATUS.md` (40 of the game's
1,481 now): the four map and city constructors (`CityMap_ctor`, `MapPeople_ctor`, `MapObjects_ctor`,
`CityRender_ctor`: the original side stops at a null jump in `MapObj_Init`'s slot call, so they were only
checked in live runs), the movie and sound shutdown paths that switch threads (`Movie_DisplayStart`,
`Movie_ResumeAll`, `Sound_Shutdown`), the memory card queue calls, and callees that only run inside others
(`File_Seek`, `Font_Free`).
